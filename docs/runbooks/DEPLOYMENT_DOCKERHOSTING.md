# Развёртывание на DockerHosting.ru

## Назначение

Этот runbook определяет минимальный безопасный порядок развёртывания Onlime CRM
на DockerHosting.ru. Текущий профиль состоит из одного контейнера с SQLite в
persistent volume. Он не является целевой конфигурацией CRM: условия перехода на
PostgreSQL, Redis и Celery зафиксированы ниже. Специфичные параметры панели,
домена, TLS и резервного копирования нужно сверять с актуальной документацией
хостинга перед первой выкладкой.

## Контракт поставки

На текущем этапе в репозитории должны появиться:

```text
Dockerfile                 # воспроизводимый образ одного приложения
compose.yml                # один сервис web и persistent volume SQLite
.env.example               # только имена и безопасные примеры переменных
```

Реальные `.env` и секреты не добавляются в Git. Production-секреты задаются в
панели DockerHosting.ru или в подключённом секрет-хранилище.

## Текущий одноконтейнерный профиль

| Сервис | Входящий трафик | Хранимые данные | Примечание |
|---|---|---|---|
| `web` | HTTP(S) через входной прокси | SQLite в обязательном persistent volume | один Django-процесс |

Ограничения текущего профиля:

- не запускать несколько экземпляров `web` с одной SQLite-базой;
- не запускать Celery, Redis, PostgreSQL, ONNX и отдельные процессы в том же
  контейнере;
- не использовать этот профиль для конкурентных склада, оплат или финансов;
- до обновления создавать резервную копию SQLite-файла и проверять восстановление.

## Условие обязательного перехода

До реализации резервирования/отгрузки/оплаты, webhook Telegram/MAX, фоновых
задач, RAG, ONNX либо горизонтального масштабирования необходимо перейти на
целевой Docker Compose-профиль: `web`, `worker`, `beat`, PostgreSQL и Redis.
`ai-worker` добавляется при тяжёлых моделях. В этом профиле PostgreSQL и Redis
не публикуют наружу свои порты и доступны только во внутренней сети.

## Обязательные переменные окружения

Шаблон находится в `.env.example`. Для production задайте значения в панели
DockerHosting.ru или подключённом секрет-хранилище:

- `DJANGO_ENV=production` и `DEBUG=False`;
- случайный `SECRET_KEY` длиной не менее 50 символов;
- `ALLOWED_HOSTS` — доменное имя или имена через запятую;
- `CSRF_TRUSTED_ORIGINS` — HTTPS-адреса публичных доменов через запятую;
- `DATABASE_PATH=/var/lib/onlime/db.sqlite3` — путь в persistent volume;
- `SECURE_SSL_REDIRECT=True`, `SESSION_COOKIE_SECURE=True` и
  `CSRF_COOKIE_SECURE=True` после настройки HTTPS на входном прокси.
- `SECURE_HSTS_SECONDS=31536000` только после проверки, что все публичные
  поддомены стабильно обслуживаются по HTTPS.

Значения секретов не выводятся в логи, CI, консольные команды или диагностические
страницы.

## Первая выкладка

1. Создать проект на DockerHosting.ru и подключить репозиторий либо загрузить
   проверенные Dockerfile/Compose-файлы.
2. Настроить production-переменные окружения и домен согласно панели хостинга.
3. Создать persistent volume для SQLite и пользовательских файлов. Подтвердить,
   что том переживает пересоздание контейнера.
4. Выполнить миграции одной одноразовой командой:
   `docker compose run --rm web python manage.py migrate`.
5. Собрать статику одной одноразовой командой:
   `docker compose run --rm web python manage.py collectstatic --noinput`.
6. Создать администратора отдельной командой, не помещая пароль в compose или Git:
   `docker compose run --rm web python manage.py createsuperuser`.
7. Запустить единственный контейнер `web` с healthcheck:
   `docker compose up -d web`.
8. Настроить публичный HTTPS-входной маршрут только к `web`.
9. Выполнить smoke-проверку: главная страница, `/health/`, вход в admin и создание
   тестового клиента после появления соответствующего доменного среза.
10. Настроить резервное копирование SQLite-файла, журналирование и уведомления об
   ошибках.

## Обновление версии

1. Проверить успешный CI, образ и совместимость миграций с текущей версией.
2. Сделать резервную копию SQLite-файла и убедиться в известном порядке её
   восстановления.
3. Применить миграции как отдельный этап: `docker compose run --rm web python
   manage.py migrate`.
4. Обновить единственный `web`-контейнер, сохранив подключение SQLite-volume:
   `docker compose up -d --build web`.
5. Проверить healthcheck, логи и критический UI-сценарий.
6. При ошибке откатывать приложение только на совместимую версию; миграции БД не
   откатывать автоматически без отдельного плана восстановления.

## Открытые вопросы до production

- Предоставляет ли выбранный тариф управляемые резервные копии томов, либо нужен
  отдельный процесс копирования SQLite-файла в объектное хранилище?
- Как на выбранном тарифе настраиваются TLS-сертификаты, домены, reverse proxy и
  WebSocket?
- Какие лимиты CPU/RAM/диска действуют для `web` на текущем этапе и для worker/
  ONNX-задач после перехода?
- Доступны ли GPU и отдельные очереди/воркеры для ONNX, если это потребуется?
- Нужны ли staging-окружение и отдельная тестовая база перед production?
