# Стратегия автоматического тестирования

## Цели

Автотесты защищают инварианты денег, склада, прав доступа и интеграций. Успех
проверки определяется не покрытием строк, а проверкой критических бизнес-рисков.

## Уровни тестов

| Уровень | Что проверяет | Среда |
|---|---|---|
| Unit | расчёты, состояния, права, доменные правила | без сети, минимум зависимостей |
| Integration, текущий этап | ORM/SQLite, миграции и веб-слой | изолированная SQLite-база |
| Integration, целевой этап | PostgreSQL, Celery, вебхуки, адаптеры | изолированные PostgreSQL и Redis |
| Contract | форматы Telegram/MAX/платежей/LLM | записанные обезличенные примеры |
| E2E | ключевые сценарии сотрудника и покупателя | Playwright + тестовая среда |
| RAG evaluation | релевантность и фильтрация доступа | обезличенный золотой набор |

## Обязательные проверки для каждого изменения

- Изменены доменные правила: unit-тесты всех затронутых переходов и ошибок.
- Изменена модель: миграция вперёд, чистая установка и обратная совместимость
  развёртывания, если применимо.
- Изменён webhook: подлинность, валидность, повторная доставка, таймауты и retry.
- Изменён UI критического процесса: E2E или функциональный тест сценария.
- Изменён доступ: позитивные и негативные проверки для ролей и организаций.
- Изменён RAG/агент: retrieval, фильтрация прав, запрет утечки и mock LLM.

## Критические тестовые наборы

### Заказ, склад и деньги

- конкурентное резервирование ограниченного остатка;
- повторная обработка платежа и webhook-событий;
- отмена и возврат с компенсацией документов;
- запрет переходов состояния в неверном порядке;
- точность `Decimal`, валюты и округления;
- неизменяемость проведённых движений.

### Безопасность

- пользователь не видит данные другой организации;
- покупатель не открывает чужую историю покупок;
- роль без разрешения не проводит заказ, резерв или финансовый документ;
- секреты отсутствуют в ответах и логах;
- webhook с неверной подписью отклоняется.

### ИИ и поиск

- поиск находит точные термины, опечатки и семантически близкие источники;
- документы другой организации исключаются до передачи контекста в LLM;
- агент не вызывает недоступный tool;
- изменяющее действие требует ожидаемого подтверждения;
- недоступность LLM не ломает основной CRM-процесс.

## CI-пайплайн

Минимальный целевой порядок:

1. Проверка форматирования и Ruff.
2. Проверка типов для нового/изменённого типизированного кода.
3. Unit-тесты.
4. Интеграционные тесты с SQLite на текущем этапе; с PostgreSQL и Redis после
   перехода на целевой профиль.
5. E2E smoke-тесты Playwright.
6. Сборка контейнера и проверка конфигурации.

Внешние сервисы в CI не вызываются. Для них используются контрактные фикстуры,
моки и тестовые реализации адаптеров.

## Тестовые данные

- Не использовать production-выгрузки или реальные персональные данные.
- Фикстуры должны быть минимальными, читаемыми и обезличенными.
- Для RAG хранить версионированный золотой набор вопросов, ожидаемых источников и
  ожидаемых ограничений доступа.
- Любой найденный production-дефект, если это возможно, сначала воспроизводится
  тестом, затем исправляется.
