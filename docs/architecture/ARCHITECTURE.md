# Целевая архитектура Onlime CRM

## 1. Стиль системы

Система строится как модульный монолит на Django. Все модули поставляются и
развёртываются одним приложением, но обладают независимыми доменными границами.
Это обеспечивает атомарность операций заказа, склада и финансов и уменьшает
операционную сложность на ранней стадии.

Выделение сервиса допускается только при наличии зафиксированного основания:
независимое масштабирование, разные требования к доступности, изолированная
безопасностная граница или доказанная командами потребность в независимой
поставке.

## 2. Слои внутри доменного модуля

```text
HTTP / WebSocket / Celery / webhook adapter
    -> application services (use cases, транзакции, права)
        -> domain rules (инварианты, состояния, расчёты)
            -> repositories/models и внешние порты
```

- Транспортный слой не содержит бизнес-правил.
- Use-case-сервис проверяет права, начинает транзакцию, вызывает доменные
  правила, записывает аудит и публикует событие после успешного commit.
- Модель Django не должна скрывать тяжёлые побочные эффекты.
- Внешние API доступны только через адаптеры; SDK поставщика не проникает в
  продажи, склад или финансы.

## 3. Модули и зависимости

| Модуль | Владеет | Допустимые направления зависимости |
|---|---|---|
| `identity` | аккаунты, организации, роли, доступ | базовый модуль для всех |
| `customers` | клиентские профили и контакты | `identity` |
| `catalog` | номенклатура, прайс, налоги | `identity` |
| `sales` | сделки, заказы, оплаты, возвраты | `customers`, `catalog`, публичные сервисы `inventory`/`finance` |
| `inventory` | склады, резервы, движения | `catalog`, `identity` |
| `finance` | финансовые документы, проводки | `identity`, публичные ссылки на `sales` |
| `customer_portal` | представление данных покупателю | публичные сервисы `identity`, `customers`, `sales` |
| `notifications` | доставка сообщений | публичные события других модулей |
| `integrations` | внешние каналы и webhook-события | публичные application services |
| `ai` | агент, документы, retrieval, модели | публичные read/write tools модулей |
| `audit` | журнал значимых действий | вызывается application services |

Циклические импорты между приложениями недопустимы. Для слабой связи используйте
явные события или публичный контракт модуля.

## 4. Данные и транзакции

### Текущий этап: SQLite

До начала реализации конкурентных CRM-процессов допускается SQLite в persistent
volume единственного контейнера. Эта БД подходит только для начальной веб-оболочки,
справочных данных и простых последовательных сценариев. Запуск нескольких
экземпляров приложения с одной SQLite-базой запрещён.

### Целевой этап: PostgreSQL

PostgreSQL — источник истины для операционных данных. Он используется для
реляционных моделей, полнотекстового и векторного поиска. Redis не хранит
авторитетное бизнес-состояние.

### Деньги, склад и документы

- Сумма: `Decimal` + ISO-код валюты.
- Количество: `Decimal` + единица измерения.
- Для каждой складской операции создаётся запись движения: приход, расход,
  резерв, снятие резерва, корректировка, инвентаризация.
- Для каждой финансовой операции создаётся документ с явным жизненным циклом.
- Исправление проведённого документа — компенсирующей операцией, а не удалением
  или неаудируемой перезаписью.
- Операции, затрагивающие несколько агрегатов, выполняются в одной транзакции
  PostgreSQL с блокировками строк при необходимости.

### Мультитенантность и доступ

Каждая бизнес-сущность принадлежит организации. Ограничение по организации и
проверка разрешения — обязательная часть каждого query/service. Отсутствие
фильтра не считается «доступом ко всем данным».

## 5. Пользовательский интерфейс

### Основной подход

Страницы строятся в Django Templates. HTMX обновляет частичные фрагменты:
таблицы, карточки, формы, фильтры, статусы и списки. Alpine.js управляет только
краткоживущим клиентским состоянием, например открытием меню или диалога.

Это позволяет использовать единую серверную валидацию, права и рендеринг ошибок.
Любой ключевой сценарий должен быть функционален без JavaScript, если реальное
время не является его сутью.

### Реактивность

- HTMX: интерактивный CRUD и серверные фрагменты.
- WebSocket через Channels: уведомления, очереди задач, мониторинг статусов,
  изменения, за которыми пользователь наблюдает в моменте.
- Redis: channel layer и уведомления о событиях.
- Не использовать WebSocket для обычной отправки форм или бесконечной синхронизации
  всех сущностей.

## 6. Асинхронные операции

После перехода на PostgreSQL Celery обрабатывает интеграции, отправку уведомлений, генерацию документов,
индексацию RAG, эмбеддинги, ONNX-инференс, импорт и экспорт.

Задача обязана иметь стабильный ключ идемпотентности, допустимый механизм retry,
таймаут, структурированные логи и корреляционный идентификатор. Публикация
задачи после изменения БД выполняется через `transaction.on_commit()`.

## 7. Интеграции

Входящие вебхуки должны:

1. Проверить подпись/секрет и минимальную корректность запроса.
2. Сохранить внешний ID события и технический факт получения.
3. Вернуть ответ провайдеру быстро.
4. Обработать событие асинхронно и идемпотентно.
5. Зафиксировать исход, ошибки и корреляционный ID.

Адаптеры Telegram и MAX переводят внешний формат в внутреннюю команду. Доменная
модель не зависит от формата сообщений и SDK конкретного мессенджера.

## 8. ИИ, RAG и поиск

### Гибридный поиск

На старте используется PostgreSQL:

- FTS — лексическое совпадение и поиск по точным терминам;
- `pg_trgm` — опечатки и похожие строки;
- `pgvector` — семантический поиск;
- Reciprocal Rank Fusion — объединение ранжированных выдач.

Фильтры организации, разрешений, статуса документа и типа источника применяются
до финального ранжирования и до передачи контекста в LLM.

### Агент

Агент получает контекст через retrieval и вызывает ограниченный набор tools.
Каждый tool имеет входную схему, правило авторизации, лимит данных, аудит и
определённый класс риска. Создавать заказ, менять цену, проводить складскую или
финансовую операцию агент может только через те же application services, что UI,
и по политике подтверждения человека.

### ONNX

Инференс ONNX не запускается в HTTP/ASGI-процессе. Воркер фиксирует версию модели,
хэш файла, параметры запуска, время и результат. Модели и эмбеддинги переиндексируются
контролируемыми пакетами, а не внутри пользовательского запроса.

## 9. Наблюдаемость и безопасность

- Структурированные логи с request/correlation ID.
- Sentry для исключений; метрики Prometheus/Grafana при запуске production-среды.
- Аудит операций, влияющих на данные, доступ, деньги, склад и интеграции.
- Ротация секретов и конфигурация через окружение/секрет-хранилище.
- Ограничение частоты запросов, CSRF, безопасные cookie, защита webhook-endpoint.
- Регулярное резервное копирование PostgreSQL и проверяемое восстановление.

## 10. Контейнеризация и Amvera

### Текущий этап

На Amvera развёртывается один контейнер `web` с приложением Django и
SQLite-файлом в подключённом persistent volume. Контейнер запускает один
прикладной процесс и не содержит Redis, Celery, PostgreSQL или ONNX Runtime.

Перед обновлением образа SQLite-файл резервируется. Обновление не должно
пересоздавать либо очищать persistent volume. Это ограниченный временный профиль,
а не целевая конфигурация CRM.

Переход на целевой профиль обязателен до реализации хотя бы одного пункта:

- параллельное резервирование, отгрузка, оплата или финансовая операция;
- обработка webhook Telegram/MAX;
- отправка уведомлений, импорт/экспорт или иная длительная задача;
- гибридный поиск, RAG, эмбеддинги или ONNX;
- несколько экземпляров `web` или требование высокой доступности.

### Целевой этап

Docker Compose — единый декларативный контракт локального запуска и CI. Целевая
production-площадка — Amvera, использующая `Dockerfile` и `amvera.yml`.
Конфигурация среды передаётся через переменные окружения, а не изменением образа
или ручной настройкой работающего контейнера.

### Состав production-развёртывания

| Контейнер | Назначение | Масштабирование |
|---|---|---|
| `web` | Django ASGI: HTTP, HTMX, webhook, WebSocket | горизонтально при необходимости |
| `worker` | обычные Celery-задачи | горизонтально по длине очереди |
| `beat` | периодические задачи Celery | строго один экземпляр |
| `ai-worker` | ONNX, эмбеддинги, переиндексация RAG | отдельно, по CPU/GPU и очереди |
| `postgres` | PostgreSQL, FTS, `pg_trgm`, `pgvector` | управляется отдельно; данные персистентны |
| `redis` | Celery broker, cache, Channels layer | управляется отдельно; не источник истины |

`web`, `worker` и `ai-worker` используют один прикладной образ с разными
командами запуска, пока реальные зависимости ONNX не потребуют отдельного
образа. Это предотвращает расхождение версий кода между процессами.

### Production-ограничения

- PostgreSQL и Redis подключены только к внутренней Docker-сети и не имеют
  опубликованных внешних портов.
- Данные PostgreSQL и пользовательские файлы сохраняются в persistent volumes
  или внешнем объектном хранилище. Нельзя хранить их только в файловой системе
  контейнера.
- Миграции запускаются как одноразовый управляемый этап выкладки, до новых
  `web`/`worker`. Автозапуск миграций каждым экземпляром приложения запрещён.
- Контейнеры запускаются от непривилегированного пользователя, имеют healthcheck,
  политику рестарта и лимиты CPU/RAM. Финальные значения лимитов выбираются после
  измерения нагрузки, особенно для `ai-worker`.
- Секреты задаются в панели Amvera либо внешнем секрет-хранилище.
  В образ, Git и compose-файл не попадают реальные ключи.
- Публично доступны только необходимые HTTP(S)-маршруты через настроенный входной
  прокси. TLS, домен и правила проксирования проверяются по актуальной
  документации Amvera перед первым production-развёртыванием.
- До миграций делается резервная копия PostgreSQL. Восстановление резервной копии
  регулярно проверяется в отдельной среде.

Операционный порядок запуска, обновления и отката фиксируется в
`docs/runbooks/DEPLOYMENT_AMVERA.md`.

## 11. Решения, которые требуют уточнения до реализации

1. Страна, налоговый режим и юридическая глубина бухгалтерского учёта.
2. Нужна ли интеграция с 1С, платёжными провайдерами, кассой или ЭДО.
3. Политика хранения персональных данных, записей диалогов и документов.
4. Требуемые SLA, ожидаемая нагрузка и необходимость GPU для ONNX.
5. Официальная спецификация и способ авторизации MAX на момент интеграции.
