# Инструкции для разработки Onlime CRM

## Назначение

Onlime CRM — крупное веб-приложение для управления продажами, клиентами,
каталогом, складом, внутренним финансовым контуром, личным кабинетом покупателя
и коммуникациями через Telegram, MAX и ИИ-агентов.

Проект разрабатывается на Python как модульный монолит. Основная цель —
надёжность бизнес-данных и быстрый, предсказуемый выпуск вертикальных функций,
а не раннее разделение на микросервисы.

Перед началом работы прочитайте `README.md`, а также относящиеся к задаче
документы из `docs/`.

## Обязательные технологические решения

- Python 3.13+ и Django 5.2 LTS.
- Текущий одноконтейнерный этап использует SQLite в persistent volume. PostgreSQL
  становится обязательной транзакционной БД до запуска параллельных операций CRM.
- Redis и Celery добавляются вместе с PostgreSQL при переходе к интеграциям,
  уведомлениям и длительным задачам.
- Django Templates + HTMX + Alpine.js — основной пользовательский интерфейс.
- Django Channels + Redis — только для действительно необходимых обновлений в
  реальном времени.
- `pgvector`, PostgreSQL Full-Text Search и `pg_trgm` — целевой гибридный поиск
  после миграции на PostgreSQL.
- На текущем этапе DockerHosting.ru запускает один контейнер приложения.

Не добавляйте отдельный SPA-фронтенд, вторую основную БД, микросервис или
очередь сообщений без ADR и явной необходимости, подтверждённой нагрузкой или
границей ответственности.

## Текущий этап: один контейнер и SQLite

- На текущем этапе приложение развёртывается одним контейнером на DockerHosting.ru.
- SQLite-файл хранится только в явно подключённом persistent volume. Нельзя
  полагаться на файловую систему контейнера: при его пересоздании данные исчезнут.
- Один контейнер не запускает несколько web-процессов, Celery worker, Celery beat,
  Redis или ONNX-инференс. Длительные и внешние операции до следующего этапа не
  реализуются как production-функции.
- SQLite не поддерживает требуемый уровень конкурентной записи для резерва,
  отгрузки, оплаты и финансовых операций. До появления любого из этих сценариев,
  webhook-обработки, RAG, фоновых задач либо необходимости горизонтального
  масштабирования обязателен переход на PostgreSQL + Redis + Celery.

## Целевой этап: контейнеры и развёртывание

- Целевая площадка production: DockerHosting.ru. Развёртывание должно работать
  из версионируемого `compose.yml` и Dockerfile без ручной настройки контейнеров
  на сервере.
- Образы собираются один раз и запускаются с разными командами: `web`,
  `worker`, `beat` и, при появлении тяжёлых моделей, отдельный `ai-worker`.
- PostgreSQL и Redis не публикуют порты в интернет. Доступ к ним только по
  внутренней Docker-сети.
- Данные PostgreSQL, Redis при необходимости персистентности и пользовательские
  файлы должны храниться в явно объявленных persistent volumes или внешнем
  хранилище. Контейнер не является хранилищем данных.
- Каждый долгоживущий контейнер имеет `healthcheck`, лимиты ресурсов и политику
  перезапуска. Процессы запускаются не от root.
- Миграции выполняются отдельной одноразовой командой release/deploy-процесса,
  а не автоматически каждым web-контейнером при старте.
- Production-конфигурация передаётся переменными окружения в панели хостинга;
  `.env` с секретами не коммитится. Перед развёртыванием проверяйте обязательные
  переменные и `DEBUG=False`.
- Перед обновлением схемы БД выполняются резервная копия PostgreSQL и проверка
  возможности восстановления. Порядок выкладки описывается в runbook.

## Целевая структура

```text
apps/                 # Изолированные доменные Django-приложения
config/               # Настройки, URL, ASGI/WSGI, Celery
templates/            # Общие и прикладные HTML-шаблоны
static/               # Исходные CSS/JS/изображения
tests/                # Сквозные и интеграционные тесты
docs/                 # Архитектура, процессы, ADR, интеграции, runbooks
```

Доменные приложения: `identity`, `customers`, `catalog`, `sales`, `inventory`,
`finance`, `customer_portal`, `notifications`, `integrations`, `ai`, `audit`.

Каждое приложение владеет своими моделями, use-case-сервисами, HTTP-представлениями
и тестами. Импорт внутренностей другого приложения запрещён: используйте
публичный сервисный интерфейс или события домена.

## Неприкосновенные бизнес-инварианты

1. Денежные суммы, налоги, цены, курсы и количества не используют `float`.
   Применяйте `Decimal`, явную валюту и единицу измерения.
2. Остатки склада, резервы и финансовые балансы не редактируются напрямую.
   Они изменяются только транзакционно через документы и неизменяемые движения.
3. Изменения статусов заказа и финансовых документов выполняются через явные
   переходы состояния с проверкой допустимости.
4. Любая значимая операция содержит автора, время, источник и correlation ID;
   значимые изменения пишутся в журнал аудита.
5. Вебхуки и фоновые задачи должны быть идемпотентны. Повтор одного внешнего
   события не может создать второй заказ, платёж или сообщение.
6. Все запросы с данными клиента обязаны фильтроваться по организации и правам
   доступа до вычисления результата, включая векторный поиск.
7. Внешний ИИ не получает прямой доступ к ORM, SQL или секретам. Агент работает
   только через разрешённые инструменты с проверкой прав и журналированием.

Подробнее: `docs/architecture/ARCHITECTURE.md`.

## Правила реализации

- Начинайте новую функцию с её бизнес-сценария, ролей и инвариантов.
- Вносите изменения схемы только Django-миграциями. Не изменяйте production-БД
  вручную.
- Оборачивайте составные изменения заказа, склада и финансов в `transaction.atomic()`.
- Длительные операции (вызовы API, ONNX-инференс, индексирование, экспорт,
  рассылка) передавайте в Celery. Не выполняйте их в HTTP-запросе.
- Делайте страницы доступными: нативные элементы форм, подписи полей,
  клавиатурная навигация, различимые ошибки, работа при отключённом JavaScript.
- Для интерактивных фрагментов сначала используйте HTMX; Alpine.js — для
  локального состояния. WebSocket добавляйте только при обоснованной потребности.
- Конфигурация и секреты читаются из окружения. В репозиторий допускается только
  `.env.example` без настоящих значений.
- Не логируйте токены, пароли, платёжные реквизиты, полные документы и лишние
  персональные данные.

## Интеграции и ИИ

- Telegram и MAX реализуются как независимые адаптеры в `apps/integrations`.
  Входящий webhook проверяет подлинность, сохраняет внешний идентификатор события
  и передаёт обработку в задачу/сервис.
- LLM-провайдеры скрываются за протоколом (интерфейсом). Доменная логика не должна
  зависеть от SDK конкретного поставщика.
- ONNX Runtime запускается исключительно в воркерах. Параметры модели,
  версия и хэш артефакта фиксируются в метаданных обработки.
- RAG использует гибридный поиск: lexical (FTS + `pg_trgm`) и semantic
  (`pgvector`) с объединением Reciprocal Rank Fusion. Перед ранжированием
  обязательно применяются фильтры организации, прав и типа документа.
- Действия агента, способные изменить данные, требуют явного разрешения и, где
  уместно, подтверждения человека.

## Тесты и качество

Каждое изменение, влияющее на поведение, должно иметь тест соответствующего
уровня.

- Unit: расчёты, права, переходы состояний, правила документов.
- Integration: PostgreSQL, миграции, Celery, вебхуки, идемпотентность, адаптеры.
- E2E: Playwright для критических пользовательских потоков.
- Contract: зафиксированные запросы/ответы внешних API.
- RAG evaluation: обезличенный набор запросов, ожидаемых источников и проверок
  запрета утечек между организациями.

Перед передачей работы запускайте узкий релевантный набор тестов, а при изменении
общего кода — полный набор проверок. Планируемый базовый набор: Ruff,
форматирование, mypy для нового типизированного кода, тесты Django и Playwright.

## Документация и решения

- Архитектурное решение с долговременными последствиями оформляйте в
  `docs/architecture/ADRs/` до или одновременно с изменением.
- Новый процесс продаж, склада, возврата или финансов документируйте в
  `docs/processes/` вместе с ролями, состояниями, инвариантами и ошибками.
- Контракты интеграций, ограничения API и правила повтора фиксируйте в
  `docs/integrations/`.
- Не переписывайте существующую документацию и чужие изменения, если они не
  относятся к текущей задаче.

## Запрещено

- Упрощать учёт денег или склада прямыми правками агрегированных полей.
- Обходить проверку прав ради удобства админки или ИИ-агента.
- Хранить секреты в коде, тестовых фикстурах, логах или документации.
- Выполнять сетевые вызовы в миграциях и синхронных доменных сигналах.
- Удалять миграции, финансовые или складские записи как способ «исправить» данные.
- Подменять архитектурное решение предположением: при неоднозначности сначала
  зафиксируйте вопрос или ADR.
